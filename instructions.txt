Important global constraints (must be enforced):

Do NOT use Redis, BullMQ, or any background job/queue system. All operations are synchronous or handled via simple HTTP/DB transactions. Long-running tasks should be simplified to synchronous calls or flagged as TODO for later (e.g., PDF generation / email sending).

Use Express (or similar) + TypeScript + Prisma (schema already provided). Use Zod for DTO validation.

Keep code transactional where multiple changes must be atomic (use Prisma transactions).

No external storage (S3) or email implementation yet — only prepare hooks / return placeholders (URL fields null or TODO). Email sending and file storage will be completed in a later milestone.

Goal (one-sentence)

Implement the manual BookingRequest → Proposal → ProposalHotel / ProposalService flow, exposing REST APIs that match the Figma flow for creating a group request, building a proposal (add hotels/services), saving as draft, and approving & sending (status change + placeholder for email/pdf).

High-level flow (matching Figma)

User creates a BookingRequest (Trip Details + Rooms + Customer fields).

User creates a Proposal tied to the BookingRequest (draft).

User adds hotels (ProposalHotel) and services (ProposalService) to the proposal.

User saves proposal as draft, previews PDF (placeholder), or approves & sends (status change & hook).

Support remove/undo hotel (soft-delete or delete + recalc totals).

Keep logs/audit events for all key actions.

API Surface (recommended, minimal)

Implement the following endpoints (CRUD + actions). Each action must validate inputs and respond with appropriate HTTP status codes and JSON payloads.

POST /api/requests

Create BookingRequest. Returns 201 with request object { id, ... }.

GET /api/requests/:id

Get BookingRequest with proposals. Returns 200.

PATCH /api/requests/:id

Update BookingRequest (trip/customer/rooms). Returns 200.

POST /api/requests/:requestId/proposals

Create Proposal (status draft). Returns 201 with proposal object.

GET /api/proposals/:id

Get Proposal (includes hotels, services, totals). Returns 200.

PATCH /api/proposals/:id

Update proposal metadata (notes, markupSettings). Return 200.

POST /api/proposals/:id/hotels

Add hotel to a proposal. Returns 201 and newly created ProposalHotel.

DELETE /api/proposals/:id/hotels/:hotelId

Remove hotel from proposal. Returns 200.

POST /api/proposals/:id/services

Add service to proposal. Returns 201.

POST /api/proposals/:id/actions/save-draft

Persist draft (set status = draft). Returns 200.

POST /api/proposals/:id/actions/send

Approve & send: set status = sent (or approved), set sentAt (column to add). Return 200. Should return an object { sent: true, sendPlaceholder: true } because email is not implemented.

POST /api/proposals/:id/actions/preview-pdf

Return a placeholder preview response (e.g., { previewUrl: null, note: "PDF generation pending" }). No background worker.

GET /api/hotels/search?q=... (optional helper)

Search hotels by name, destination, starRating, amenity filter. Returns a list.

// src/validation/requestSchemas.ts
import { z } from "zod";

// Rooms object in BookingRequest
export const RoomsSchema = z.object({
  single: z.number().int().min(0).default(0),
  double: z.number().int().min(0).default(0),
  twin: z.number().int().min(0).default(0),
  triple: z.number().int().min(0).default(0),
  quadruple: z.number().int().min(0).default(0),
  suites: z.number().int().min(0).default(0),
  extraRoomsNote: z.string().trim().max(2000).nullable().optional(),
});

// Create BookingRequest
export const CreateBookingRequestSchema = z.object({
  source: z.string().optional(),
  companyName: z.string().min(1),
  contactName: z.string().min(1),
  contactEmail: z.string().email(),
  contactPhone: z.string().min(5),
  currencyCode: z.string().min(2).max(10),
  destinationId: z.number().int(),
  destinationName: z.string().min(1),
  checkinDate: z.string().refine((d) => !isNaN(Date.parse(d)), { message: "Invalid date" }),
  nights: z.number().int().min(1),
  rooms: RoomsSchema,
  nationalityCode: z.string().min(1).max(10).optional(),
  budget: z.number().positive().optional(),
  specialRequirements: z.string().max(5000).nullable().optional(),
  status: z.enum(["pending", "draft"]).optional(),
});

// Create Proposal
export const CreateProposalSchema = z.object({
  notes: z.string().max(5000).optional(),
  markupSettings: z.record(z.any()).optional(), // more strict structure can be added
});

// Add Proposal Hotel
export const AddProposalHotelSchema = z.object({
  hotelCode: z.string().min(1),
  tid: z.string().optional(),
  rooms: z.record(z.object({
    net: z.number().nonnegative(),
    sell: z.number().nonnegative(),
    qty: z.number().int().nonnegative(),
    nights: z.number().int().nonnegative()
  })).optional(),
  currency: z.string().min(2).max(10),
  totalPrice: z.number().nonnegative(),
  freeCancellation: z.boolean().optional(),
  cancelDeadline: z.string().optional().nullable().refine((v) => !v || !isNaN(Date.parse(v)), { message: "Invalid date" }),
  supplierCode: z.string().optional(),
  optionDetailsId: z.string().optional()
});

// Add Proposal Service
export const AddProposalServiceSchema = z.object({

Add Hotel to Proposal (details)

Validate with AddProposalHotelSchema.

Check the proposal exists and status allows modification (e.g., not sent or declined).

Use a single Prisma transaction to:

Create proposal_hotels record with provided fields (rooms saved as JSON).

Recalculate totalBuy and totalSell by aggregating proposal_hotels + proposal_services for that proposal and update proposal.totalBuy/totalSell.

If optionDetailsId provided, store it in proposal_hotels.optionDetailsId (helps later for caching).

Respond 201 with the created ProposalHotel and updated Proposal totals.

Important: If hotel tid or option details are needed but not in cache, simply store the provided tid and mark optionDetailsId null — do not call an external service synchronously. Leave a TODO to later fetch if required.

Add Service to Proposal (details)

Validate using AddProposalServiceSchema.

In a transaction:

Create proposal_services record.

Recalculate totals (aggregate proposal_services buyPrice/sellPrice plus proposal_hotels.totalPrice).

Update proposal.totalBuy/totalSell.

Respond 201 with the created service and updated totals.

Concurrency, locking & multi-user editing (no Redis!)

Because Redis/queues are disallowed in this milestone, use only DB-level techniques and simple locks:

Optimistic Edit Lock:

Add proposal.lockedBy (userId) and proposal.lockedAt (timestamp).

When a user opens the Proposal for editing, client should call POST /api/proposals/:id/actions/lock which sets lockedBy to the user and lockedAt = now() if lockedBy is null or lockedAt older than a configured timeout (e.g., 15 minutes).

To release, call POST /api/proposals/:id/actions/unlock or release automatically on save/send.

Lock enforcement should be advisory: when attempting to modify a locked proposal by another user, return 409 Conflict with the lock owner info.

Transactions:

Use Prisma transactions (prisma.$transaction) for sequences: add hotel -> recalc totals -> update proposal totals. This prevents partial writes.

Row-level concurrency:

Where available, use optimistic concurrency via an updatedAt timestamp: require clients to provide If-Unmodified-Since or expectedUpdatedAt in updates to detect stale edits. If mismatch, return 409 Conflict.

Use a consistent decimal type (Prisma Decimal) to persist buy/sell/total values; use decimal.js or Prisma Decimal in application code for arithmetic to avoid float precision issues.
