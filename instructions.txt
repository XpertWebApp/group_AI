Project overview (one-paragraph for sharing)

SETT AI Group Offer Agent — Phase 1: backend API (Node.js + Express + TypeScript) that exposes secure REST endpoints
 and a webhook to ingest group booking requests, stores requests and generated offers in PostgreSQL 
 (multi-schema: auth, master, app, cache, audit), integrates with the WBE / SetHub availability APIs 
 (SearchAndGetByHotelsV2 → OptionDetailsV2 → GetUpdatedOptions), caches supplier OptionDetails in DB, and provides 
 admin endpoints for offer review. Uses Prisma ORM, follows MVC + Service + Repository pattern, centralized error 
 handling, validation, structured logging, and is production-ready behind Nginx and PM2. No Redis in Phase-1.

 0) High level goals to implement

Initialize a Node.js (v18+) + TypeScript backend repository (server/) following MVC + Service + Repository pattern.

Use Prisma for Postgres ORM with multi-schema support (auth, master, app, cache, audit).

Implement secure authentication (JWT access + refresh tokens), role-based access.

Implement webhook endpoint to ingest booking requests. Persist raw payload + normalized fields.

Integrate WBE.hotel APIs flow for Phase-1 (SearchAndGetByHotelsV2, OptionDetailsV2, GetUpdatedOptions) — implement API client and caching for OptionDetails.

Provide basic endpoints for requests / offers / proposals and admin flows (list, get, create [manual], add hotel to a proposal).

Set up migrations, seeds, linting, testing, logging, CI skeleton, Dockerfile, Nginx reverse proxy config, and PM2 deployment skeleton.

1) Which static APIs to call (order)

GET /api/hotel/destinations?apiKey=...

GET /api/hotel/masterfacilities?apiKey=...

GET /api/hotel/Hotels?apiKey=... — returns hotel list with HotelCode, HotelDetailsUrl.

For each hotel (in controlled batches): GET {HotelDetailsUrl} — returns detailed hotel info (images, master facilities, full description).

Always include apiKey in the query string per WBE docs.

2) Minimal recommended schema tweak (one small change)

Add parent_id to master.destinations so you can store the hierarchical data returned by destinations. Also add fields to master.hotels to mark whether details were fetched.

Suggested lines:

-- master.destinations
parent_id int    -- nullable, FK -> master.destinations.id

-- master.hotels additions
hotel_details_url text
details_fetched_at timestamp
last_synced_at timestamp   -- already present, confirm it exists

(You already have hotel_details_url and last_synced_at in your schema — confirm details_fetched_at and parent_id exist.)

3) Field mapping (API → tables)
Destinations

API returns countries + nested destinations (DestinationId, Name, ParentDestinationId).
Map to:

master.destinations

id ← DestinationId (int)

name ← Name

parent_id ← ParentDestinationId (nullable)

country_code / region as provided for top-level country object

metadata ← raw chunk or additional JSON for that node (optional)

last_synced_at ← now()

Master Facilities

API returns list of { Id, Name }.
Map to:

master.facilities

id ← Id (int)

name ← Name

created_at

Hotel list (light)

The Hotels API returns array with MasterHotelId, HotelCode, DestinationId, Name, StarRating, PropertyType, Category, GiataId, HotelDetailsUrl.
Map to master.hotels:

hotel_code ← HotelCode (PRIMARY KEY / unique)

master_hotel_id ← MasterHotelId

hotel_details_url ← HotelDetailsUrl

destination_id ← DestinationId

name, star_rating, property_type, category, giata_code

last_synced_at ← now() when upserted

metadata ← null or minimal if you want to keep entire list response

Hotel details (full)

GET HotelDetailsUrl returns full JSON with HotelId, HotelCode, Name, Latitude, Longitude, StarRating, Category, Location, Description, Email, Address, AddressCity, AddressCountry, Phone, PropertyType, RoomFacilities, HotelFacilities, MasterFacilities[], Images[].

Map to:

master.hotels.metadata ← full JSON (store to inspect easily)

update fields in master.hotels (address, lat/long, giata, phone, etc)

master.hotel_images ← each item in Images[] as image_key and display_order

master.hotel_facilities ← map each MasterFacilities entry (FacilityId => facility_id)

master.hotel_facility_groups ← optionally persist RoomFacilities and HotelFacilities (category + facilities array), OR normalize into master.hotel_facilities as you prefer

set details_fetched_at and last_synced_at to now

Important: keep the raw JSON in master.hotels.metadata (or another column) so you can re-map fields later without re-fetching.

4) Safe, idempotent data persistence strategy (upsert + transactions)

Principle: each static import must be idempotent — repeated runs should not create duplicates and should update changed rows only.

For each top-level call:

Wrap the per-entity DB operations in a single transaction or use safe upsert primitives.

Use ON CONFLICT/upsert semantics (Prisma upsert() or raw SQL upsert) keyed on natural unique fields:

master.destinations.id (PK int)

master.facilities.id (PK int)

master.hotels.hotel_code (PK)

master.hotel_images unique on (hotel_code, image_key) or use id pk and upsert by hotel_code+image_key.

master.hotel_facilities unique on (hotel_code, facility_id)

Example flow (no code, outline):

GET /api/hotel/Hotels → returns array of hotels.

For each hotel chunk (e.g., 200 items):

In transaction:

upsert row in master.hotels (match on hotel_code) with returned fields and hotel_details_url.

mark last_synced_at = now() for updated rows.

After upserting list, batch fetch hotel details (see concurrency).

For each HotelDetails response:

In transaction:

update master.hotels with extra fields (address, lat/long, etc), set metadata = raw JSON, set details_fetched_at.

upsert images into master.hotel_images (match by hotel_code + image_key).

upsert master facilities mapping into master.hotel_facilities (match hotel_code + facility_id).

optionally clear and reinsert facility groups (fast approach: delete where hotel_code = X then insert new rows inside same transaction).

On error, rollback and log to audit.api_calls with error info.

5) Efficiency, rate-limit, and reliability rules

Batching / chunk size: fetch hotel details in batches of e.g. 25–50 concurrently (configurable). Too much parallelism risks API throttling.

Retry + backoff: for transient 5xx or network errors, implement exponential backoff (3 retries).

Respect supplier guidance: weekly sync recommended — do not hammer their API.

Concurrency throttling: run a worker queue that fetches details with a concurrency limit (e.g., p-limit).

Use audit.api_calls: record every external call (endpoint, payload, status code, response, duration_ms). This helps debugging and retries.

Checksum/ETag: If WBE returns anything like VersionDescription or ETag, check it and skip update when unchanged. If not available, compute a small hash of the relevant fields (name + address + last_synced_at) and skip if hash unchanged to avoid unnecessary writes.

Temp staging for big imports: optionally insert into a temp table and run a single INSERT .. ON CONFLICT sweep to reduce transactions on huge imports.

6) Scheduling & triggers

Weekly cron (e.g., 0 3 * * 6) to update static data. Steps:

GET /api/hotel/destinations → upsert destinations (parents first).

GET /api/hotel/masterfacilities → upsert facilities.

GET /api/hotel/Hotels → upsert hotels list (light).

Launch a detail fetch worker that iterates hotels with details_fetched_at IS NULL OR last_synced_at < (now - 7d) in batches and fetches HotelDetailsUrl.

Manual admin endpoint to trigger full re-sync on demand (protected route).

Backfill process: when adding new suppliers or missing details, admin can schedule on-demand re-fetch.

7) Auditing & monitoring

Log every external API call into audit.api_calls including status and duration.

On failures, create a small alert record or send email to devops if repeated failures occur.

For long imports, write progress into a cache.search_sessions-like table or a sync_jobs table (optional) to get status and run reports.

8) Index and query considerations

Index master.hotels(destination_id) and master.hotels.name for fast lookups during hotel search.

Index master.hotel_facilities(hotel_code) and (hotel_code, facility_id) for fast joins.

master.hotel_images(hotel_code, display_order) for fetching gallery ordered.

master.destinations(parent_id) to traverse hierarchies quickly.

Keep metadata and data columns as JSONB but avoid heavy queries on them; extract searchable fields into columns (e.g., latitude, longitude, address_city) for indexing.

9) Edge cases & tips

HotelCode is case-sensitive and unique — always store exactly as returned.

HotelCode length varies; your varchar(255) is safe.

Some hotels may not have HotelDetailsUrl — handle gracefully (mark as details_fetched_at = NULL and retry later).

Some hotel details images keys are encoded — combine base CDN URL + image_key when rendering on front end. Store only image_key in DB.

Facilities may be returned as strings or MasterFacilities ids. If both exist, prefer master id mapping.

10) Where this lives in your app (code responsibilities)

StaticDataService (server/src/services/staticData.service.ts):

orchestrates the calls in the above order.

retries, chunking, and concurrency control.

calls repositories to upsert entities.

logs to audit.api_calls.

StaticDataRepository (server/src/repositories/...):

implements upsert primitives with Prisma for each model (destination, hotel, facility, images).

performs SQL transactions when inserting related entities per hotel.

Scheduler:

cron job / node-cron or systemd timer that triggers StaticDataService.

Admin API:

secure endpoint POST /admin/static-sync to trigger manual sync.

Cron triggers static-sync job.

Service calls GET /api/hotel/destinations. Upsert destinations (parents first, then children), set last_synced_at.

Service calls GET /api/hotel/masterfacilities. Upsert master.facilities.
